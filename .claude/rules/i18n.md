# Internationalization (i18n)

## Core Rules

- **No hardcoded strings**: All user-facing text must use translation keys, never inline strings.
- **Translation files**: Store translations in structured files (JSON/YAML) per locale, e.g. `locales/en.json`, `locales/de.json`.
- **Default locale**: Always define a fallback locale. Missing translations must fall back gracefully, never show raw keys to users.

## Implementation

- Use the project's i18n library (e.g., `next-intl`, `i18next`, or Go equivalents) consistently.
- Translation keys should be namespaced by feature/page: `auth.login.title`, `dashboard.stats.label`.
- Pluralization, date/time, and number formatting must use locale-aware APIs — never manual string building.
- Keep translations separate from code logic. Components receive translated strings, not locale identifiers.

## Best Practices

- New user-facing features must include translation keys from the start — do not add i18n retroactively.
- Right-to-left (RTL) support: use logical CSS properties (`margin-inline-start` over `margin-left`) where applicable.
- Avoid string concatenation for sentences — different languages have different word orders. Use interpolation placeholders.
- Review translations for context — the same word may translate differently depending on usage.
